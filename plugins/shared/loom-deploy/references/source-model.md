# Deploy Source Model Reference

Use this reference when Loom selects `deploy.source-model`. It explains how repository evidence becomes deployable services.

## Source Model Contract

`DeploymentSourceModel` is generated by Loom and is the authority for deployment asset generation.

Required closure:

- `services[].serviceId` becomes the Compose service id and Dockerfile suffix.
- `services[].role` decides public frontend, backend API, or single app behavior.
- `services[].root` is the repository-relative source root.
- `services[].workingDirectory` is the in-container command directory when it differs from the build context.
- `services[].runtimeKind` selects the stack generator.
- `services[].packageManager`, `hasLockfile`, `manifestRefs`, and `lockfileRefs` drive dependency install commands.
- `services[].buildCommand`, `startCommand`, `outputDirectory`, `port`, and `healthcheckPath` are generated service facts. They must agree with Dockerfile, Compose, and validation; runtime command authority comes from `runtimeContract.commands.development`, `verification`, and `deployment`.
- `manifestRefs` and `lockfileRefs` must contain only files confirmed by the repository scanner. Never emit a wildcard or a conventional manifest that does not exist.
- A healthcheck path is optional. Absence means Loom validates the preview/API probe externally; it must not be replaced with `/`.
- `storageFacts` are the only source for file-database and dependency volume mounts. Do not infer persistence from an environment string or a fixed container directory.

Agents should not rediscover this model from logs. If the model is wrong, use the returned `modelRepairRef` and state which source fact is inconsistent. Do not edit `source-model.json` directly or replace it with an unrelated topology; Loom validates the base fingerprint, recalculates dependent facts, and regenerates assets after an accepted model repair.

## Layout Rules

Root app:

- Source root is `.`.
- Build context may be the repository/app root.
- Dockerfile copy paths are root-relative.

Split frontend/backend:

- Frontend roots are usually `web`, `frontend`, `client`, or `ui`.
- Backend roots are usually `service`, `backend`, `api`, or `server`.
- Frontend and backend must have separate service records unless a backend-served static topology is proven.

Workspace app:

- Roots under `apps/*`, `services/*`, or `packages/*` need the workspace root as build context when root lockfiles/workspace manifests are required.
- Dockerfile must switch to the app working directory before build/start commands.
- Build context, Dockerfile path, `COPY` sources, and `WORKDIR` must form one valid triangle.

Same-root fullstack:

- One runtime project contains both backend and frontend assets.
- Frontend output must be copied into the backend artifact/static directory before runtime start.
- Do not create a frontend gateway unless the source model has a separate frontend service.

## Runtime Family Expectations

Node:

- Detect package manager from lockfile and `packageManager` metadata.
- Use production preview/server commands, not dev servers, unless no production script exists.
- Preserve Linux optional dependency handling in generated images.

Java:

- Maven/Gradle wrapper or build file determines package manager.
- Spring Boot, Quarkus, and Micronaut need runtime port/env consistency.
- Runnable jar discovery must avoid `*-plain.jar`, sources, and javadoc jars.

Python:

- `requirements.txt`, `pyproject.toml`, `uv.lock`, `poetry.lock`, `manage.py`, `main.py`, `app.py`, or `server.py` identify app roots.
- Framework entrypoints must bind to `0.0.0.0`.

Go:

- `go.mod` identifies the module root.
- Build output should be a single runtime binary copied into a slim runtime image.

.NET:

- `*.csproj`, `*.sln`, `global.json`, and ASP.NET package signals select SDK/runtime images.
- Published DLL selection must not assume a fixed assembly name unless detected.

PHP:

- `composer.json`, `artisan`, and `public/index.php` identify Composer/Laravel-style apps.
- Runtime should serve the correct document root and not require host PHP.

Ruby:

- `Gemfile`, `config.ru`, and Rails config identify Bundler/Rails/Rack apps.
- Runtime directories such as `tmp`, `log`, and `storage` must exist for Rails-style apps.

Static:

- Existing static output such as `dist`, `build`, `public`, `out`, `_site`, or root `index.html` can be served directly.
- Do not invent an API service for a static-only app.

## Preflight Checklist

Before startup, validation should catch:

- Service id missing from Compose.
- Service root missing inside build context.
- Manifest or lockfile refs missing inside build context.
- Dockerfile `COPY` sources outside the build context.
- Dockerfile `WORKDIR` not aligned with service root.
- Dockerfile `EXPOSE` not aligned with `sourceModel.port`.
- Generated `.dockerignore` excluding required manifests or lockfiles.
