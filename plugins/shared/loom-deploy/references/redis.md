# Redis Deployment Reference

## When To Use

Load this reference only when the accepted RuntimeDependency projection contains a Redis dependency. The accepted TechnicalBaseline capabilities are authoritative for whether Redis exists and why it is needed.

## Runtime Facts

- Redis service identity comes from the canonical dependency projection.
- The default internal service name is `redis` and the default container port is `6379`.
- Application connection URLs use Compose DNS such as `redis://redis:6379`.
- Redis must not receive a host port unless the accepted runtime port plan explicitly marks one public.
- Code probes may report Redis candidates, but they cannot override an accepted RuntimeDelivery contract.

## Capability Projection

- Cache-only ephemeral capability: no data volume is required; application fallback behavior remains part of the architecture contract.
- Any persistent capability: create the named volume and mount it at the generated Redis data path.
- Required Redis capability: generate `redis-cli ping` healthcheck and make dependent application services wait for `service_healthy`.
- Queue and Stream capabilities must preserve the accepted persistence and retry boundary; do not turn them into an unbounded generic cache.
- Separate dependency ids are required when capabilities need independent isolation or incompatible eviction and durability policies.

## Generated Asset Expectations

- Compose contains one service for each accepted dependency projection.
- Redis uses a pinned image tag, internal `expose`, and no accidental host `ports` entry.
- Persistent Redis output contains the named volume in both the top-level volume declaration and the service mount.
- Healthcheck, `depends_on`, service name, and connection URL refer to the same Redis service.
- Generated Dockerfiles for application services do not copy `.env`, `.loom`, local databases, or Redis credentials.

## Verification Focus

- `docker compose config` resolves the Redis service, volume, healthcheck, and dependency condition.
- The application connects through the Compose service name rather than container-local `localhost`.
- Cache, Session, Queue, and Stream capability projections match the accepted runtime facts.
- A missing Redis candidate does not create a service from repository keyword evidence.

## Repair Boundary

Repair generated Compose and generated deployment assets when the source model and accepted runtime facts are correct. Do not repair Redis topology by editing application source or by adding a provider that is absent from the accepted contract.

If the accepted capability model is wrong or incomplete, stop asset repair and request an upstream TechnicalBaseline or RuntimeDelivery correction. Do not make the Agent reconstruct capability semantics from a Docker error.

## Out Of Scope

Sentinel, Cluster, replication, production backup, monitoring, TLS, and registry operations are not generated by the local Loom deployment path.
