# React Native Project Structure And Configuration

Change project structure only when the task owns app configuration, a framework migration, reusable mobile architecture, or frontend-experience scaffolding. Preserve the repository's established Expo/bare-native and feature/module boundaries.

## Discover The Existing Shape

Inspect package/workspace roots, app entry, `app/` routes or navigator setup, `src/`/feature folders, platform projects, Expo config, Metro/Babel config, TypeScript/JavaScript config, tests, assets, and generated native files before adding directories.

Identify whether `ios/` and `android/` are source-owned bare projects, generated by Expo prebuild, or intentionally absent. Do not edit generated native output when the repository expects config plugins and repeatable prebuild.

Respect monorepo package boundaries and Metro watch/resolver configuration. A module that TypeScript resolves may still fail in Metro, Jest, CocoaPods, Gradle, or EAS/native builds.

## Route And Feature Placement

In Expo Router, route files own route composition, param intake, and layout metadata. Move reusable screens, feature components, data hooks, services, validators, and stores outside route folders unless they are genuinely route-local.

In React Navigation, keep navigator declarations separate from reusable screen implementation once the hierarchy is non-trivial. Avoid a central navigator importing every feature's infrastructure directly.

Organize by established feature/domain boundaries before inventing global `utils`, `helpers`, or `common` buckets. Shared UI primitives must not import product-domain services; feature components may compose primitives with domain behavior.

Keep API, auth, analytics, storage, notifications, permissions, and native adapters behind explicit typed modules. Services should not own screen navigation or hidden UI state transitions.

## App Configuration

Treat bundle/package identifiers, app name/slug, schemes, associated/universal links, permissions, plugins, orientation, tablet support, icons, splash assets, runtime/version policy, update channels, and build properties as release-impacting configuration.

Merge environment-specific settings through the repository's config mechanism. Do not hardcode development hosts, credentials, signing values, or provider IDs in source config.

When adding a config plugin or native dependency, confirm compatible Expo SDK/React Native versions, plugin ordering, generated changes, required permissions, and whether a development-client/native rebuild is required.

## Tooling Configuration

Keep Metro, Babel, TypeScript, Jest, Reanimated, and path aliases aligned. If an alias is introduced, update every resolver that consumes it rather than making editor/typecheck success the only proof.

Preserve required plugin ordering such as the repository's Reanimated/worklets convention. Do not copy version-specific plugin rules without checking installed packages.

Use the repository language policy. Do not convert JavaScript projects to strict TypeScript as an incidental structure change; migration requires explicit ownership and complete tooling coverage.

## Assets And Fonts

Place assets where Metro/Expo/native config can resolve them. Confirm exact path/case, supported format, dimensions, scale variants, licensing, font loading, and fallback behavior.

Do not reference a generated, local-only, or ignored asset path. App icons and splash assets require platform-specific shape/size/background checks, not only an in-app render.

## Dependency Boundaries

Prefer dependencies already approved in the repository. For a new package, verify maintained platform support, Expo compatibility, native setup, license, bundle/binary impact, and replacement/fallback behavior.

Avoid circular imports among routes, features, components, stores, and services. Keep barrel exports narrow when they obscure cycles or pull native-only modules into shared code.

## Migration And Moves

Move files in buildable slices and update route discovery, imports, tests, mocks, Metro/Jest aliases, native registration, and asset references together. Do not leave parallel old/new module ownership after cutover.

Preserve route names, deep links, storage keys, analytics IDs, and public package exports unless the accepted change explicitly migrates them.

## Verification

- Run focused TypeScript/JavaScript checks, Metro bundle/start, tests, and affected platform build/config validation.
- Use the repository Expo doctor/prebuild or native dependency checks when SDK, plugins, or native modules change.
- Prove aliases resolve in Metro and tests, not only in the editor/typechecker.
- Verify route discovery, config schemes/permissions, referenced assets/fonts, and generated-native expectations.
- Check dependency cycles and ensure generated native output is reproducible from source configuration.

## Delivery Evidence

Name the source-owned app root, route-versus-feature boundary, config/dependency change, generated/native ownership, and commands proving all resolvers/build paths agree. A tidy folder tree alone does not establish runtime or release correctness.

## Unsafe Defaults

- A new folder taxonomy imposed on an established project.
- Reusable implementation left inside Expo route files.
- Generated `ios/`/`android/` files edited when prebuild owns them.
- Alias configured only in TypeScript.
- Native dependency added without plugin/rebuild/platform compatibility checks.
- App identifiers, schemes, permissions, or environment hosts copied from examples.
